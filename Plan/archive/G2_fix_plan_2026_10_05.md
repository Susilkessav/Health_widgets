## A — Fix local presentation correctness first

### A1. P1: Separate local refresh from uploading

**Files:** `App/AppModel.swift`; add a small testable scheduling/lifecycle policy in the core if necessary.

Remove the upload-enabled requirement from scheduling local BGAppRefresh. Split lifecycle ownership: a local/store generation invalidates work on store/account replacement; a network generation invalidates only upload work when uploading is toggled. `cancelUploads()` currently cancels local background refresh too, and local catch-up compares `uploadGeneration`, so merely removing the scheduling guard is insufficient.

Schedule after a completed local catch-up and local refresh task, including when uploads are disabled. Gate only network work on upload preference. Preserve cancellation on expiry, account/store replacement and explicit local reset. Keep iOS scheduling best effort.

**Acceptance:** upload-disabled startup/catch-up schedules local refresh; toggling uploads off mid-import does not prevent local recalculation/publication; scope replacement cannot publish old-store results; expiry completes once; observer imports remain coherent. Real-device check: a HealthKit change reaches the widget without opening the app while uploading is disabled.

### A2. P2: Calculate day/freshness at display time

**Files:** `LocalCalculation.swift`, `AppModel.swift`, `DebugView.swift`, `ExplanationView.swift`; reuse `WidgetPolicy` where appropriate.

Treat persisted `isToday` as historical transport metadata, not the clock authority. Define one display policy using the calculation day, current time and device timezone, consistent with the widget. The app must reevaluate at foreground, midnight and timezone changes, including when an import fails. Daily traits and missing-input descriptions from an earlier day must not pose as today's. Preserve absolute-time workout fading. If a timezone change makes the saved calculation ambiguous, display it as a previous result until recalculation rather than rewriting its health meaning.

**Acceptance:** before/after midnight; DST spring/fall; timezone travel in both directions; offline retained result; failed refresh; explanation open across rollover. App/widget agree on whether daily traits are current. “Updated” continues to mean the calculation's effective time.

### A3. P2: Make widget explanations honest about the linked result

**Files:** `HomeostatApp.swift`, widget URL construction, `AppModel.openExplanation`, `ExplanationView.swift`.

Parse and validate the scheme, host, scope and nonnegative run ID. For a matching current local run, explain that run. For a same-scope older run, use the current result with an explicit “This result has been updated” message identifying the linked/current runs. For another scope or an unavailable result, show an unavailable message without presenting a different user's result. Freeze the explanation snapshot while displayed.

**Chosen scope:** use this explicit latest-result fallback for G2; do not introduce a historical run ledger merely to fix a link. Exact retained-run explanations can be added later with a retention policy. Local and server run ID namespaces remain distinct.

**Acceptance:** matching run; newer result arrives before/after tap; another scope; missing/malformed/duplicate query parameters; no local result. No silent result substitution. The final app bundle registers `homeostat://`; `simctl openurl` now reaches iOS’s Open confirmation. Resolver cases are automated; confirming a tap through the native UI remains in device acceptance.

### A4. P2: Preserve unknown cache payloads on reads

**Files:** `HomeostatShared/SharedWidgetStore.swift`, `WidgetState.swift`, shared-store tests.

Separate coordinated read and mutation operations. `read()` and `manifest()` must not re-encode, migrate, create or overwrite the file. Continue safe neutral rendering for invalid/unsupported avatars. Migrate legacy cache formats only during an intentional compatible write. Keep writing atomic, coordinated and protected. An unsupported outer manifest must remain untouched; recovery/reset stays explicit.

**Acceptance:** byte-identical disk contents after repeated reads of valid, malformed-avatar, future-avatar and legacy files; safe fallback for unsupported versions; compatible write migration; corrupt-file handling; concurrent reader/writer behavior; existing scope/order protections retained. Review widget-client mutations too so they do not accidentally discard unknown payloads while updating fetch metadata.

### A5. P2: Schedule every time-driven render transition

**Files:** `AvatarState.swift`, `AvatarView.swift` (`AvatarPose`), `WidgetPolicy.swift`, shared tests.

Keep half-life intensity math and the documented strict cutoff unchanged. Compute the first representable timeline instant at which the effect is actually below 0.05, including exact-boundary cases. Add the crossing where glow stops exceeding the 0.4 stretching threshold. Centralize render transition calculation beside the rendering policy so timeline and painter cannot drift. Include future-start/clock-grace transitions for supported cached timestamps, freshness, lighting and midnight; keep dates sorted, deduplicated and bounded to the timeline horizon.

The pose test currently proves pose selection only; it does not prove the widget has an entry for its transition. At peak 1, the 160-minute glow crosses 0.4 at approximately 3 h 31 min, not “the first two hours.” Update the comment/spec to the actual confidence-dependent rule rather than changing the rule implicitly.

**Acceptance:** peaks 0, below cutoff, exactly cutoff, 0.1, 0.5 and 1; before/at/after disappearance; both sides of 0.4; sweat priority over glow; low/high motion fallback; future start and grace; midnight truncation; DST. Every emitted transition entry draws the expected pose/effect. Verify on a Home Screen because iOS may delay timeline delivery.

## B — Make verification and supporting APIs reliable

### B1. P2: Replay empty and incomplete device databases safely

**Files:** `DeviceReplayTests.swift`, `backend/app/device_check.py`, replay-helper tests.

Distinguish uninitialized storage from initialized empty readings.

Use a consistent SQLite backup/export including committed WAL contents for physical-device evidence. Record database-copy identity, timezone, engine/config versions and checkpoint count, without committing private health payloads.

**Acceptance:** no events with valid coverage; no coverage; partial domain coverage; missing stored result; withdrawn observations; quarantined records; normal phone export. Python/Swift agree on generated checkpoints, including avatar. Preserve the original T4 phone-database evidence; rerun on a fresh phone export when performing final device acceptance.

### B2. P2: Fix configuration identity for custom settings

**Files:** `EngineSettings.swift`, feature/state JSON serialization, calculation APIs, parity tests.

Current production uses `.standard`; custom mutable settings nevertheless produce the default hash. Carry the actual settings identity in derived results and serialize that identity. Define canonical encoding matching the Python configuration schema, with cross-language vectors for custom configurations. Keep the default hash byte-for-byte unchanged. If custom settings cannot be supported correctly in this patch, reject them explicitly at the exported calculation boundary until a separate configuration patch lands; never label a nondefault result as default.

**Acceptance:** standard hash unchanged; a threshold change yields a distinct hash; the feature and health-state hashes agree; Python/Swift canonical vectors match. Preserve the 170 default parity checkpoints. Version/serialization compatibility must be reviewed before changing public result structs.

### B3. P2: Bound server bodies while receiving them

**Files:** `backend/app/main.py`, API tests.

Keep authentication before ingestion. Count bytes from the request stream and return 413 immediately on exceeding `MAX_BODY_BYTES`; do not first assemble an arbitrary body. Preserve existing valid-request bytes and receipt/idempotency behavior.

**Acceptance:** exact limit succeeds; limit plus one rejects; chunked/no Content-Length rejects oversized data; misleading header cannot bypass the cap; valid retry retains the same receipt; unauthorized request remains rejected. Run these checks with PostgreSQL.
