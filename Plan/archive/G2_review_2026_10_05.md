# G2 review — 2026-10-05

## Result and scope

The on-device architecture is a sound foundation for G2. Avatar presentation
is already partially implemented in the working tree, despite the plan and
tracker calling it unstarted. Review covered the current G2 plan/tracker,
related G1/on-device plans, Python/Swift avatar mapping and contracts, local
calculation/publication, cache policy, app/editor/demo, widget and tests.
This review records recommendations; it does not approve G1 or G2 acceptance
or change the implementation or existing plan.

## Preview and verification

- App and widget Debug build succeeded for the iPhone 18 Pro simulator.
- Built app installed and launched; the captured screen shows the avatar editor.
- Generated and visually reviewed the existing render-test contact sheet:
  `G2_avatar_preview.png`. Simulator capture: `G2_simulator_preview.png`.
- Backend: 3,562 non-database tests passed; 164 database-dependent tests excluded;
  two dependency deprecation warnings.
- Swift: 29 shared and 75 core tests executed with zero failures. Two initially
  skipped: optional contact-sheet export and device-database replay. Contact-sheet
  export subsequently passed, leaving real-device replay unverified.
- All 170 parity checkpoints passed. Compared with the committed G1 fixture,
  feature and HealthState outputs remain identical; their configuration hashes
  remain unchanged. This verifies the current corpus, not every possible input.
- Physical-device background delivery, widget memory, actual widget layouts,
  tinted mode and VoiceOver were not verified by this run.

## Improvements, ordered by priority

### P1 — Before treating G2 as accepted

1. **Reconcile progress and the entry gate.** `G2_tracker.md` says “Not started”
   while T1–T3 and portions of T6–T10 exist. Record each as implemented,
   verified or pending acceptance. G1 physical-iPhone acceptance remains open
   in the documents; either record evidence or explicitly revise the sequencing
   decision. Do not mark work complete solely because files exist.

2. **Validate Swift avatar payloads before caching/rendering.** Swift Codable
   currently accepts unrestricted doubles and a free-form avatar version;
   `WidgetState` also permits a missing avatar for v0.2. Python requires an
   avatar and enforces ranges, unique effect kinds and eye/activity consistency.
   Match these invariants in Swift. Unsupported nested versions and malformed
   avatars need a defined fallback that preserves usable text/last-valid data.
   Test malformed caches as well as valid round trips.

3. **Bound timeline generation.** `WidgetPolicy.timelineDates` converts
   `halfLifeMinutes * 60` to Int64. A positive half-life under one second becomes
   a zero step, so its while loop cannot advance; very large values can also
   overflow conversions/date arithmetic. Validate sensible bounds, guarantee
   progress, cap entry count and jump directly to the next future transition.
   Python's positive-float constraint alone does not exclude these cases.

4. **Define freshness independently from effects.** T8 promises neutral stale
   avatars with uncertainty. The widget actually keeps the original avatar
   and fades the whole layout to 60%; earlier-day entries retain the original
   traits too. Define whether old eyes/posture/movement become neutral or remain
   explicitly historical, then apply that consistently in app, widget and
   accessibility text. Preserve time-based workout effects separately if desired.

5. **Make decay independent of recalculation timing.** A six-hour glow has 25%
   intensity at twelve hours and does not reach the 5% cutoff until about
   26 hours at peak 1. The mapper removes it when G1 changes from recent_workout
   to none_recent after twelve hours. A cached avatar can therefore keep glowing
   while a newly calculated one loses it at the same time. Specify an explicit
   lifetime or derive effects from the last workout driver independently of the
   classification. Verify midnight, the twelve-hour boundary, corrections,
   deletions and repeated calculations. Whole_project §9 says effects must not
   reset at midnight.

6. **Add channel provenance before freezing the contract.** The plan promises
   Driver IDs for every channel, but the current flat AvatarState and Effect
   omit them. Recovery has multiple contributing sleep/HRV/RHR drivers rather
   than one recovery driver. Define per-channel evidence references, including
   multiple references for posture and workout source evidence for effects.
   Environment is clock-derived and needs no fabricated health driver.

7. **Make the demo exercise the real pipeline.** T10 calls for parity fixture
   checkpoints, but AvatarDemoView constructs handwritten AvatarStates. Its
   “Missing HRV” preset cannot prove the mapper handles missing HRV correctly.
   Bundle selected real widget states, their effective time/timezone and text;
   keep manual states as a separate visual playground. Include actual stale,
   no-data, low-confidence and mixed-domain states.

### P2 — Contract, rendering and product quality

8. **Resolve specification drift explicitly.** Plan proposes layered artwork in
   a HomeostatAvatar target; current renderer is Canvas inside HomeostatShared.
   Plan identity counts and intensity levels differ from code/tracker; the
   plan specifies a backend/avatar.py module while mapping lives in
   presentation.py. Record the adopted prototype design and final-art migration
   path. Update T0 to cover D1–D10 and correct the D1 reference to motion in T9,
   not T10.

9. **Publish an exact mapping table.** D7 says confidence scales channels,
   but only eyes and effect peaks scale; posture and motion are categorical.
   Specify severity ranges, intensity quantization, threshold inclusivity,
   neutral states and how combinations behave. Add focused tests around
   confidence 0.5, independent domain changes and all supported workout labels.

10. **Represent uncertainty by domain.** The current marker checks sleep,
    recovery and movement but excludes workout. Missing HRV can still permit
    recovery from sleep/RHR and show no marker. Decide whether uncertainty means
    unavailable inputs or uncertain visible channels. Store reason/domain
    information for explanations rather than one unexplained global question mark.
    Keep valid channels visible when another channel is unknown.

11. **Choose effect behavior before its start.** Current tests deliberately
    show full intensity before started_at. Specify whether pre-start effects
    should be zero, or whether clock skew is handled with an explicit tolerance.
    This matters for demos and future historical replay. Cover future timestamps
    and cutoff boundaries without relying on a live clock.

12. **Improve readability at real widget sizes.** The contact sheet shows subtle
    upright/neutral differences, eye detail obscured by glasses and low leg/body
    contrast at night. Define readable pose differences, preserve eye contrast
    for every skin tone/accessory and constrain lighting washes. Review both
    crops with text at actual sizes, rather than enlarged avatar images alone.

13. **Add light/dark/tinted rendering rules.** The tracker mentions tinted mode,
    but current rendering has no explicit widget rendering-mode treatment.
    Specify which visual channels survive a single-color presentation, with
    shape/text cues for activity rather than glow color alone. Validate dark
    and increased-contrast appearances as separate scenarios.

14. **Replace render-smoke checks with reviewed snapshots.** Current tests check
    non-null pixels and unique images; an unintended visual regression can still
    satisfy both. Keep those checks, and add stable reviewed baselines for real
    parity states, widget layouts, identities, crops and appearance modes.
    Store baseline images and identify the renderer/OS used to produce them.

15. **Use evidence-based accessibility language.** “Looks well rested” currently
    follows above-baseline sleep duration, which does not establish subjective
    rest. “Sweating” is a visual effect inferred from a workout, not a sensor
    observation. Describe the visual and its recorded cause; include uncertainty,
    freshness and all visible channels. Verify VoiceOver ordering and Dynamic
    Type on complete widgets/editor screens. Swatch buttons are 34 points;
    give them larger hit areas and more descriptive accessible names.

16. **Make identity saves truthful and durable.** AppModel changes its in-memory
    identity before saving. A failed write only logs an error, and an unavailable
    App Group silently succeeds through optional chaining. Commit only after a
    successful write or show a retryable unsaved state. Add identity schema
    versioning/migration and verify app/widget agreement after restart, locked
    device access, corruption and scope resets.

17. **Separate animation scheduling from time updates.** Reduce Motion pauses
    the entire animation TimelineView, potentially leaving lighting/decay frozen
    until another redraw. Use a slower clock update for time-dependent rendering
    while breathing/blinking are disabled. The comment says tired eyes blink
    slower, but the code uses a shorter period (3 versus 4.5 seconds); resolve
    that discrepancy. Measure foreground/background animation cost.

18. **Define complete widget fallback/privacy behavior.** Empty/unreadable states
    still show emojis; v0.1 caches become an unknown neutral avatar despite the
    plan mentioning an emoji fallback. Decide and document these choices. Small
    widgets omit detail/secondary text, so ensure the surviving text explains the
    visual adequately. Apply a deliberate privacy/redaction policy to the avatar
    and headline, which currently expose health traits while only detail and
    secondary lines are marked privacy-sensitive.

### P3 — Execution and verification plan

19. **Make signing and physical-device checks concrete.** The plan assumes a free
    Personal Team and no paid capability, while app/widget sharing relies on App
    Group entitlements. Confirm the actual signing setup and shared-container
    availability on the phone; simulator success is insufficient. Record the
    outcome as a gate rather than assuming the environment supports it.

20. **Make acceptance reproducible.** Add exact build/test commands, fixture
    regeneration instructions, phone database-copy/replay procedure, device/OS,
    expected outputs, evidence location and pass/fail criteria. T4's “no code”
    label should still include this verification work. Distinguish data import
    age, calculation time and widget rendering time in diagnostics. Define
    measurable memory/CPU budgets and observe background delivery over the
    existing 24–48 hour G1 acceptance window.

21. **Add CI and versioned replay policy.** No CI workflow was found in this
    checkout, despite the plan saying CI runs both suites. Run backend checks,
    Swift parity and iOS/widget builds in CI. Enforce unchanged HealthState
    fixtures/configuration identity. The backend presentation version changed
    to 0.2 and replay rejects runs with other versions; explicitly document
    whether old runs are replayable via version dispatch or intentionally
    reported unsupported. Include compatibility tests for old stored payloads.

22. **Clarify task dependencies and scope.** T4 verification depends on both
    mappers even though the diagram branches directly from T2; the first slice
    promises a rendered phone avatar while omitting T6. Give each task an owner,
    deliverable and evidence gate, and separate placeholder prototype completion
    from final art and device acceptance. Keep the separate workout/agent
    architecture proposal outside G2, while sharing provenance/action contracts
    where useful. Resolve art source, licensing/export specifications and the
    asset manifest before final-art integration.

## Recommended sequence

Reconcile plan/status and G1 evidence → validate contracts and bound timelines →
settle freshness, decay and provenance → use real fixtures in the demo → review
widget snapshots/accessibility/appearance → verify signing, memory and background
behavior on the phone → record G2 acceptance.
