# On-device calculation — plan (2026-09-30)

Status: phases 1–4 implemented 2026-09-30; real-iPhone acceptance open.

Decision: Homeostat calculates on the iPhone for now. The FastAPI backend is
kept, tested and documented, but it is no longer on the path from Health data
to the widget. It returns when the product needs something only a server can
do (see "Server, later").

Why: the server can't read HealthKit, so the phone must import everything
anyway. Without always-on hosting (deferred), a server path only works at home
and the widget goes stale elsewhere. Everything the calculation needs is on
the phone.

## Target flow

```
HealthKit → ImportEngine → LocalStore (events, coverage, deletions, generations)
          → LocalInputs (observations + context for "now")
          → Engine: selection → features → HealthState → WidgetState   (Swift port)
          → LocalStore "local_state" → App Group WidgetCache → widget
```

Runs after every import: app open/foreground, HealthKit background delivery,
BGAppRefresh. The calculation is milliseconds; no network.

## Phases

1. **Engine port** (`HomeostatCore/Engine/`, pure Swift, no GRDB/HealthKit):
   settings (defaults = `backend/config/homeostat.yaml`), selection (retries,
   tombstones, conflicts), sleep episodes/primary/baseline, HRV/RHR robust z,
   movement pacing, workouts, confidence, state engine, presentation.
   *Parity test:* a fixture generated by the Python pipeline for every golden
   scenario and demo checkpoint; the Swift result must match (numbers within
   1e-9, strings exactly). Python stays the reference.
2. **Local inputs**: event log = `event_outbox` bodies (all canonical events,
   uploaded or not); coverage = `coverage_outbox` rows except `withheld`;
   lost-anchor withdrawal done locally (a type whose current generation has
   completed its scan keeps only that generation's members); effective time =
   the common import cutoff for today.
3. **App wiring**: calculate after each import; store as `local_state`;
   the widget cache, explanation screen and debug screen read it. Works with
   no server configured (a device-scoped store). The widget's server fetch is
   off. "Send Health data to the server" stays optional: it only uploads, so
   the server keeps a history for later.
4. **Docs**: README/Next_steps point here; the server sections are marked
   "later".

## Not ported (server-only, later)

Replay/rebuild and stored run ledger, installation-scoped visibility scans
(the device does withdrawal locally), revisions/receipts, widget credentials,
device accounts and pairing. Their code and tests stay in `backend/`.

## Server, later

Bring the server back into the result path when one of these is needed:
- a second device or platform (Android, web) must show the same result;
- a wearable cloud API (Oura, Whoop, Garmin) delivers data server-side;
- an audit/replay trail of every published result is required;
- always-on hosting is chosen.

What already exists for that: canonical event contract (phone uploads are
unchanged), ingestion/idempotency, recalculation worker, replay, device keys
and pairing, widget read tokens. What will be needed: hosting + backups,
deciding whether the server result supersedes the local one (proposal: the
server wins for multi-source accounts; single-iPhone accounts keep local),
and keeping the Swift and Python engines in lockstep via the shared parity
fixture.
